# Implementation Plan: Clinic Onboarding, Staff Creation, and Dual Authentication

**Branch**: `003-clinic-onboarding-staff` | **Date**: 2026-04-06 | **Spec**: `specs/003-clinic-onboarding-staff/spec.md`
**Input**: Feature specification from `/specs/003-clinic-onboarding-staff/spec.md`

## Summary

Extend the Petiatrics platform with a gated clinic onboarding flow, username-based staff provisioning, and a dual-path login system. The implementation targets three layers simultaneously: the Prisma schema (new status values, slug field, username field, nullable email), the NestJS API (new public registration endpoint, admin approval/rejection actions, refactored login and staff creation), and the Next.js frontend (registration page, updated login form, updated admin clinic list, updated staff page, forced-password-change page).

The guiding implementation principle is to make the minimum targeted changes to each file in the existing monorepo rather than introduce new modules or new apps. All tenant isolation rules established in spec 002 remain in force: `clinicId` is always derived from the authenticated session context, never from a client-supplied body field.

## Phase 0: Research

See [`research.md`](./research.md) — 12 decisions covering all NEEDS CLARIFICATION items.
All items resolved. No outstanding unknowns.

**Key decisions summary:**
1. Extend `IdentityModule` — no new module
2. Server-side slug generation at `registerRequest()` time; numeric suffix for collisions
3. Single `identifier` field in login DTO; slug-based resolution lookup
4. Extend `ClinicStatus` with `PENDING`/`REJECTED`; `UserStatus` with `PENDING`
5. `User.email` → nullable; add `username`, `mustChangePassword`, `name`
6. `mustChangePassword` stored in Redis session; clinic layout enforces redirect
7. Per-endpoint `@Throttle(10, 60)` override on the public registration route
8. `approve`/`reject` as `PATCH` verbs in `AdminController`; run in `$transaction`
9. Replace `invite()` with `createStaff()` entirely; backward compat via email path, not invite endpoint
10. `UserContext.email` and `AuthProfile.email` become optional (`string | null | undefined`)
11. `name` field added to `User`; staff list returns `name` and `username`
12. New `(auth)/register/page.tsx`; `/register` added to middleware `PUBLIC_PATHS`

## Implementation Phases

### Phase A — Foundation (schema + shared types)

These files must land in a single commit before any backend or frontend work begins, because TypeScript compilation across all packages depends on them.

| # | File | Change | Risk |
|---|------|--------|------|
| A1 | `packages/database/prisma/schema.prisma` | Add `PENDING`/`REJECTED` to `ClinicStatus`; add `PENDING` to `UserStatus`; add `slug String @unique`, `phone String?` to `Clinic`; add `name String?`, `username String? @unique`, `mustChangePassword Boolean @default(false)` to `User`; make `email String?` (drop `@unique` on email alone — unique is now a separate `@@unique` if needed, see note) | **High** — nullable email migration requires `DROP NOT NULL`; slug backfill must run before `NOT NULL`+`@unique` is enforced. Migration sequence documented in data-model.md. |
| A2 | `packages/database/prisma/` | Run `npx prisma migrate dev --name 003-clinic-onboarding` to generate migration SQL, then `npx prisma generate` to refresh the Prisma client | **Medium** — backfill migration must handle existing clinic rows (slug from name) and existing user rows (email stays, mustChangePassword=false). |
| A3 | `packages/types/src/enums.ts` | Add `PENDING = 'PENDING'`, `REJECTED = 'REJECTED'` to `ClinicStatus`; add `PENDING = 'PENDING'` to `UserStatus` | Low — additive only. |
| A4 | `packages/types/src/api.ts` | Change `email: string` → `email?: string \| null` in `UserContext` and `AuthProfile`; add `username?: string \| null`, `mustChangePassword?: boolean` to both | **Medium** — removing `email` non-null guarantee will surface TypeScript errors at every call site that assumes email is always present. Compile errors guide fixes. |
| A5 | `packages/database/src/seed.ts` | Update seed to set `slug` on seeded clinic, `name`+`username` on seeded staff user | Low — seed only; no prod impact. |

> **Note on `User.email` uniqueness**: The current schema has `email String @unique`. After making it nullable, Prisma/PostgreSQL allows multiple `NULL` values on a nullable unique index. No extra `@@unique` composite is needed. Staff users will have `email = null`; the unique constraint on `username` prevents collisions there.

### Phase B — Backend Services

Depends on Phase A (Prisma client must be regenerated before services compile).

| # | File | Change | Risk |
|---|------|--------|------|
| B1 | `apps/api/src/modules/identity/services/clinic.service.ts` | Add `registerRequest(dto: RegisterRequestDto): Promise<Clinic>` — generate slug, set `status=PENDING`, wrap in `$transaction`. Add `approve(clinicId: string): Promise<void>` — set `status=ACTIVE`, emit audit. Add `reject(clinicId: string, reason: string): Promise<void>` — set `status=REJECTED`, emit audit. Update `getAll()` to include `slug` and owner name. | **Medium** — slug collision retry loop; stale-state race between two concurrent approvals. Mitigated by Prisma `$transaction` and a unique constraint on `slug`. |
| B2 | `apps/api/src/modules/identity/services/user.service.ts` | Add `createStaff(clinicId: string, dto: CreateStaffDto): Promise<User>` — build `username = dto.usernamePrefix + '@' + clinic.slug`, hash a random temp password, set `mustChangePassword=true`. Remove (or keep on a deprecation path) `invite()`. | **Medium** — `username` must be unique; race condition if two admins create staff with same prefix simultaneously. Unique index on `username` will throw; handle with a 409 response. |
| B3 | `apps/api/src/modules/identity/services/auth.service.ts` | Replace `LoginDto.email` with `LoginDto.identifier: string`. Add resolution logic: if identifier contains `@`, split into `prefix@slug`; look up `Clinic` by `slug`, then `User` by `username = identifier`; fall back to email lookup if no clinic found by that slug. Add `PENDING` user status check (throw 403). Include `mustChangePassword` in session write. | **Low-Medium** — resolution adds one extra Prisma read for staff logins (slug lookup). Capped by Redis session cache for subsequent requests. |

## Risk Register

| Risk | Severity | Phase | Mitigation |
|------|----------|-------|------------|
| `slug` backfill on existing clinic rows fails migration | **High** | A2 | Migration runs `UPDATE` with slugified `name` before adding `NOT NULL`; test on a dump of staging data before applying to production. |
| `User.email` nullable change surfaces compile errors throughout codebase | **Medium** | A4 | TypeScript compilation after Phase A surfaces all breakage locations; treat as a guided checklist. All crashes at compile time, not runtime. |
| Redis sessions for in-flight authenticated users lack `mustChangePassword` key | Low | D7 | `SessionService.getSession()` already backfills missing fields with defaults; add `mustChangePassword: false` to the backfill map. |
| Slug collision during concurrent clinic registrations | Low | B1 | Prisma `$transaction` + a unique index on `Clinic.slug`; retry loop in service (max 9 numeric suffixes, then nanoid(4)). |
| Staff username collision (two admins create same prefix concurrently) | **Medium** | B2 | Unique index on `User.username` enforced by DB; service catches Prisma `P2002` and returns 409 to controller. |
| Change-password redirect loop (`mustChangePassword=true` user on /clinic/change-password) | Low | D7, D8 | Layout redirect guard: only redirect when `mustChangePassword === true` AND `pathname !== '/clinic/change-password'`. |
| Old `/clinic/staff/invite` callers break after C3 endpoint removal | Low | C3 | The `staff-client.tsx` is the only existing caller; replaced in D6. No external API consumers documented. |
| SUPER_ADMIN email accidentally treated as a staff username during login | Low | B3 | Resolution logic checks `User.username` field; SUPER_ADMIN users have `username = null`, so `@`-containing input falls back to email lookup and succeeds on the email path. |

## Implementation Sequence

```
Phase A (Foundation)  →  Phase B (Backend Services)  →  Phase C (Backend Controllers)
                                                                    ↓
                                                          Phase D (Frontend)
```

Within Phase D, steps D1–D3 can be done in any order. D4–D8 depend on D1–D3 being complete (middleware and i18n keys must exist first). D7 and D8 must be done together to avoid the redirect loop.

The recommended commit sequence:
1. `feat(schema): add PENDING/REJECTED enums, slug, username, nullable email` — covers A1–A3, A5
2. `feat(types): email optional, add username and mustChangePassword to UserContext` — A4
3. `feat(clinic): registerRequest, approve, reject, slug generation` — B1
4. `feat(user): createStaff replaces invite` — B2
5. `feat(auth): identifier resolution, PENDING check, mustChangePassword session` — B3
6. `feat(controllers): register-request, change-password, approve/reject endpoints` — C1–C3
7. `feat(web): middleware PUBLIC_PATHS, i18n keys` — D1–D2
8. `feat(web): login identifier field` — D3
9. `feat(web): clinic registration page` — D4
10. `feat(web): admin clinic pending/approve/reject UI` — D5
11. `feat(web): staff usernamePrefix UI` — D6
12. `feat(web): mustChangePassword redirect + change-password page` — D7–D8
