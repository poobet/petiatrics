# Implementation Plan: Inventory & Stock Management

**Branch**: `008-inventory-management` | **Date**: 2026-06-01 | **Spec**: [spec.md](./spec.md)

---

## Summary

Extend the existing `InventoryModule` to support full transactional stock tracking: Goods Receipt, Goods Issue (with FEFO enforcement), Manager-approval Stock Adjustments, and in-app Low Stock alerts. The schema evolution adds `lotNumber`/`expiryDate`/`version` to `BranchStockBalance`, a `status` + lot fields to `StockMovement`, and a new `StockAlert` model. The clinical module's existing `deduct()`/`replenish()` flows are preserved unchanged.

---

**Language/Version**: TypeScript 5.x (strict mode)
**Primary Dependencies**: NestJS 10, Next.js 14 App Router, Prisma 5, shadcn/ui, EventEmitter2, class-validator

**Testing**: Jest + ts-jest (`*.spec.ts`), Playwright (E2E, `apps/web/test/`)
**Target Platform**: Docker-based monorepo (local + CI + prod parity)
**Project Type**: Full-stack web service (NestJS API + Next.js frontend)
**Performance Goals**: Balance queries < 200ms p95; movement commit < 500ms p95
**Constraints**: Optimistic locking for concurrent writes; bilingual UI (EN + TH); tenant isolation from session context
**Scale/Scope**: Multi-branch clinic; tens of thousands of movement records per clinic per year

## Constitution Check

### Principle I — Domain Boundaries Are Enforceable ✅
All stock operations remain within `InventoryModule`. The clinical module's `deduct()`/`replenish()` are preserved. No cross-module schema reach-through is introduced. New `StockAlert` model is owned by the inventory domain.

### Principle II — Tenant Isolation Comes From Trusted Server Context ✅
`clinicId` is extracted from server-side session via `@TenantId()` decorator on all new endpoints. `branchId` is validated against the session's authorized branches. Client payloads cannot supply `clinicId`.

### Principle III — Session Security And Auditability Are Mandatory ✅
Every `StockMovement` write captures `actorId` from the session. FEFO override reasons are stored in the immutable `StockMovement` record. `StockAlert` lifecycle changes are logged. `@Audit()` decorator applied to all mutation endpoints.

### Principle IV — Specs, Plans, Tasks, And Tests Must Align ✅
This plan references `spec.md` acceptance criteria. Tasks must include unit tests for the service layer and contract tests for the API. High-risk paths (negative stock, optimistic lock conflict, FEFO override) require explicit test coverage.

### Principle V — Production Parity And Bilingual Delivery Are Defaults ✅
All new UI strings added to `messages/en.json` and `messages/th.json`. No new local-only infrastructure. Feature runs in Docker via existing `docker-compose.yml`.

**Gate result**: PASS — no violations. No complexity tracking entry required.

## Implementation Sequence

The implementation is organized into 4 phases ordered by dependency. Each phase is independently deployable and testable.

---

### Phase 1: Schema & Migration (Foundation)
**Dependency**: None — must complete first
**Risk**: Medium (nullable column additions to live tables; unique constraint change)

1. Add `lotNumber`, `expiryDate`, `version`, `updatedAt` to `BranchStockBalance`
2. Change unique constraint on `BranchStockBalance` to `[clinicId, branchId, productId, lotNumber]`
3. Add raw SQL partial unique index for `lotNumber IS NULL` rows
4. Add `lotNumber`, `expiryDate`, `overrideReason`, `approverId`, `status` to `StockMovement`
5. Add `StockMovementStatus` enum (`COMMITTED`, `PENDING_APPROVAL`, `REJECTED`)
6. Add `GOODS_RECEIPT`, `GOODS_ISSUE` to `StockMovementReason`
7. Add `StockAlert` model + `StockAlertType` enum
8. Run `prisma migrate dev` and verify existing data integrity
9. Run existing `stock.service.spec.ts` — must pass unchanged (backward compat check)

---

### Phase 2: API — Core Stock Movements
**Dependency**: Phase 1
**Risk**: High (optimistic locking, FEFO logic, negative-stock enforcement)

1. Add `goodsReceipt()` to `StockService`:
   - Validate product exists and belongs to clinic
   - Enforce `lotNumber`/`expiryDate` if `requiresBatchAndExpiryTracking`
   - Upsert `BranchStockBalance` (create or increment); increment `version`
   - Write immutable `StockMovement` (status = COMMITTED, reason = GOODS_RECEIPT)
   - Emit `stock.low_stock_warning` if applicable; call `resolveAlerts()` if now above reorderPoint
   
2. Add `getIssuableLots()` to `StockService`:
   - Query `BranchStockBalance` for product/branch, ordered `expiryDate ASC NULLS LAST, lotNumber ASC`
   - Return list with `isFefo`, `isExpired`, `quantity` flags

3. Add `goodsIssue()` to `StockService`:
   - Validate chosen lot exists and has sufficient quantity
   - If chosen lot ≠ FEFO lot: require `overrideReason` (throw `BadRequestException` if missing)
   - If chosen lot is expired: require `overrideReason`
   - Decrement `BranchStockBalance.quantity` using optimistic lock (`where: { id, version }`)
   - On version mismatch: throw `ConflictException` ("Stock was modified concurrently; please retry")
   - On quantity < 0 after deduct: throw `ConflictException` ("Insufficient stock")
   - Write immutable `StockMovement` (status = COMMITTED, reason = GOODS_ISSUE)
   - Emit `stock.low_stock_warning` if balance ≤ reorderPoint

4. Add new routes to `StockController`:
   - `POST /inventory/stock-movements` → `goodsReceipt()` or `goodsIssue()` based on `movementType`
   - `GET /inventory/stock-balances` → paginated balance list with status computation
   - `GET /inventory/stock-balances/lots/:productId` → FEFO-ordered lot list

5. Write DTOs: `GoodsReceiptDto`, `GoodsIssueDto`, `ListStockBalancesDto`

6. Tests:
   - `stock.service.spec.ts`: goodsReceipt, goodsIssue, FEFO override, expired lot, negative stock, optimistic lock
   - `stock.controller.spec.ts`: happy path + 409 responses
   - `inventory-stock.contract.spec.ts`: API contract tests for new endpoints

---

### Phase 3: API — Adjustments & Alerts
**Dependency**: Phase 2
**Risk**: Low-Medium

1. Create `StockAdjustmentService`: `submitAdjustment()`, `approveAdjustment()`, `rejectAdjustment()`
   - Submit: write `StockMovement` with `status = PENDING_APPROVAL`, `reason = MANUAL_ADJUSTMENT`; compute variance
   - Approve: within a transaction, update balance + write final COMMITTED movement with `approverId`
   - Reject: set `status = REJECTED`, store `overrideReason` (rejection reason)

2. Create `StockAdjustmentController` with `@Roles(MANAGER, ADMIN)` guards

3. Modify `LowStockListener` to call `StockAlertService.upsertAlert()` instead of only logging

4. Create `StockAlertService`: `upsertAlert()`, `resolveAlert()`, `listActive()`

5. Create `StockAlertController`: `GET /inventory/alerts/low-stock`

6. Tests: adjustment service (submit/approve/reject state machine), alert upsert/resolve

---

### Phase 4: Frontend
**Dependency**: Phase 2 complete (can start Phase 4 in parallel with Phase 3)
**Risk**: Medium (FEFO UX, compliance field gating, optimistic lock error handling)

1. **Stock Ledger page** (`/inventory/stock-ledger`):
   - `StockLedgerTable` component — uses `GET /inventory/stock-balances`
   - Status badge computed from quantity vs reorderPoint vs expiryDate
   - Branch filter (Manager: all branches; Staff: own branch only)
   - Slide-over panel: paginated movement history per item
   - Action buttons: "New Receipt", "New Issue", "Adjust Stock"

2. **Goods Receipt page** (`/inventory/receipt`):
   - `GoodsReceiptForm` component
   - Item search with barcode input field
   - Conditional Lot/Expiry fields — shown and required based on `requiresBatchAndExpiryTracking`
   - Validation blocks submit if compliance fields missing
   - On success: toast + redirect back to ledger

3. **Goods Issue page** (`/inventory/issue`):
   - `GoodsIssueForm` component
   - Lot selector populated from `GET /inventory/stock-balances/lots/:productId`
   - First lot marked "FEFO Recommended" badge
   - `FefoOverrideDialog` triggers if non-FEFO lot selected
   - Expired lot shows red banner + mandatory override reason
   - Inline "Insufficient stock" error on 409

4. **Adjustments pages** (`/inventory/adjustments`):
   - Pending Approvals list for Manager — approve/reject with confirmation dialog
   - New Adjustment form with variance display

5. **Low Stock Banner** (`low-stock-banner.tsx`):
   - Polled every 30s via `GET /inventory/alerts/low-stock`
   - Dismissable amber strip on main inventory layout
   - Notification bell badge count in app shell

6. **i18n**: Add `inventory.stock.*` keys to `messages/en.json` + `messages/th.json`

7. **E2E tests** (Playwright): Goods Receipt happy path; Goods Issue FEFO deviation; Low Stock alert visibility

## Key Risks & Mitigations

| Risk | Phase | Mitigation |
|---|---|---|
| Prisma partial unique index on nullable `lotNumber` | 1 | Raw SQL in migration; tested in migration verify step |
| Existing stock.service tests break on schema change | 1 | All new fields nullable; existing test mocks unchanged |
| Negative stock under concurrent load | 2 | Optimistic lock + service-layer pre-check; 409 with retry guidance |
| FEFO override bypass | 2 | Server-side: chosen lot ≠ FEFO lot → `overrideReason` required; BadRequestException |
| Clinical module DISPENSE flow broken | 2 | `deduct()` not modified; runs regression tests in Phase 2 |
| Bilingual UI missed | 4 | i18n keys are a Phase 4 task; CI lint checks for missing translation keys |
